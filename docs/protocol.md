# Protocol and design

## Design

- Small API of our own types; no quic-go type appears in it.
- `Listen` serves many peers on one socket; each package `Dial` uses its own socket and nothing is shared between dials, while `Listener.Dial` reuses the listener's socket, its NAT mapping and its `Config`.
- `ListenConn` takes ownership of the caller's `PacketConn` unconditionally, so a failed call never leaks it.
- Non-QUIC datagrams are capped at 1200 bytes, the size QUIC starts with, so they fit any path QUIC works on.
- `Conn.Context` wraps quic-go's connection context and maps its cause, so no quic-go error or peer text escapes through `context.Cause`.
- Bidirectional streams for request and reply, unidirectional ones for one-way data; streams carry raw bytes.
- Datagrams are not exposed: unreliable messages need their own size, queue and rate limits.
- Keep-alive is always on. quic-go sends a PING after min(`KeepAlivePeriod`, idle timeout / 2) without receiving anything, raised to at least 1.5 times the probe timeout. A connection stays open while the peer answers and ends after the idle timeout once the peer or the path is gone. Close connections you no longer need, and accept the ones that arrive. Each side's idle timeout is min(own `IdleTimeout`, max(peer's `IdleTimeout`, 5s)), because quic-go raises the peer's value to at least 5s (`connection.go`), so below 5s the two sides can time out at different moments.
- `HandshakeTimeout` bounds the whole handshake; `IdleTimeout` applies after it.
- Every limit has a default and a hard maximum, checked before anything is opened. The receive windows are advanced options with small defaults (256 KiB per stream, 512 KiB per connection), and `MaxIncomingStreams` defaults to 16, because with 1-byte frames each unread byte costs about 176 bytes of heap and each byte read on a stream still open keeps about 96 (measured); `MaxMemory` checks that `MaxConns` plus `MaxDialed` connections fit.
- Receive windows start small for every connection (256 KiB per stream, 512 KiB per connection) and are fixed unless `WindowGrowth` is on. Then quic-go's auto-tuning can grow them, up to `MaxGrown*` ceilings, but only for a connection the application marked with `Conn.AllowWindowGrowth`, which the transport cannot do itself because it does not authenticate peers, and only while `MaxGrownMemory`, a budget shared by the listener's connections and given back when a connection ends, has room (quic-go's `AllowConnectionWindowIncrease`). Nothing is added to the wire: the windows are the QUIC flow control limits (RFC 9000 section 4) the receiver advertises.
- Congestion control is a choice of the sending end and adds nothing to the wire. The default is quic-go's Reno sender; `Config.CongestionControl` `"bbr"` replaces it with the BBR controller of `internal/bbr` through the hook `internal/quicgo/PATCH` adds to the vendored quic-go, on every connection the `Config` makes, and the hook builds the controller again when a path migration resets the connection's sender. See the guide, "Congestion control".
- ALPN is `kolo/0`; a peer offering anything else fails the handshake.
- Fixed, not options: TLS 1.3 only, QUIC version 1 only, no session tickets, no resumption, no 0-RTT (`Listen`, never `ListenEarly`) and Retry always on.
- The listener's certificate is an ephemeral self-signed Ed25519 one generated by `Listen`; the dialer presents none.
- A new connection attempt needs a valid Retry token (RFC 9000 section 8.1.2): one more round trip, and no state is kept for an address until it has answered. NEW_TOKEN tokens are expired at any age, even after the wall clock steps back (`MaxTokenAge` is the smallest duration, since a token's age is measured with the wall clock and can be zero or negative), so they never skip Retry. A Retry token can be reused from the same IP, from any port, for `HandshakeTimeout` (measured with the wall clock), so attempts from an address that has answered once are bounded by `MaxConnsPerIP`, not by Retry.
- Amplification: QUIC drops client Initials under 1200 bytes and limits a server to 3 times the bytes received from an address it has not validated; with Retry, the listener answers an unvalidated address only with a Retry, a version negotiation packet or a CONNECTION_CLOSE (INVALID_TOKEN, for a bad Retry token), each smaller than the packet that caused it.
- `AcceptFunc` runs inside quic-go's `Transport.ConnContext`, the earliest hook that sees an IP that answered a Retry: after the address check, before the per-address and total counters.
- Connections are counted per source address from the start of their handshake, so one address cannot hold every `MaxConns` slot with stalled handshakes or idle connections; this is sound because only addresses that answered a Retry are counted.
- No separate cap on handshakes in progress: a stalled handshake frees its slot after `HandshakeTimeout`, and an open connection kept busy holds one as long, so only the per-address cap helps against either.
- Flood of Initials: quic-go queues at most 1024 unprocessed packets for new connections and drops the rest, and sends at most a few Retry or refusal packets at once, dropping the others. Each Initial without a valid token costs one token encryption and one Retry, with no state kept. Attempts that pass Retry count against `MaxConns` and `MaxConnsPerIP` from the start of their handshake and are refused (CONNECTION_REFUSED) beyond them; quic-go also refuses handshaked connections when 32 wait for `Accept`. Not bounded: the number of distinct addresses, so peers on more than `MaxConns / MaxConnsPerIP` addresses that answer Retry can still fill `MaxConns`; the heap: unread data is bounded at run time by (`MaxConns` + `MaxDialed`) × `MaxConnReceiveWindow` (`MaxMemory` only checks that product), but with 1-byte frames its heap is about 176 times that, plus about 96 times the stream window retained per open stream, about 84 GiB for the `MaxConns` connections plus about 27 GiB for the `MaxDialed` ones at the defaults (measured, see [limits.md](limits.md)); on the side of the package `Dial` nothing caps the number of connections (`Listener.Dial` has `MaxDialed`), so a node that dials N peers can be made to hold N × `MaxConnReceiveWindow` unread, about 176 times that in heap, plus retention; the CPU and bandwidth spent per packet; and the OS UDP receive buffer (quic-go asks for 7 MiB), which drops packets when full, those of open connections included.
- Errors map peer close and reset to sentinels plus numeric codes; reason phrases from the peer are dropped.

## Formats

The wire format is QUIC version 1 (RFC 9000) with TLS 1.3 (RFC 9001), ALPN
`kolo/0`. Error codes are QUIC varints, 0 to 2^62-1. Stream contents are
the application's bytes; there is no JSON form.

## References

- [RFC 9000, QUIC: A UDP-Based Multiplexed and Secure Transport](https://www.rfc-editor.org/info/rfc9000) (Proposed Standard, May 2021).
  Takes: QUIC version 1, Retry on every new connection (8.1.2), 1200-byte first packets (14), stream and error-code semantics.
  Not implemented: 0-RTT, session resumption, QUIC version 2 (RFC 9369), unreliable datagrams (RFC 9221).
- [RFC 9001, Using TLS to Secure QUIC](https://www.rfc-editor.org/info/rfc9001) (Proposed Standard, May 2021).
  Takes: the TLS 1.3 handshake inside QUIC, ALPN `kolo/0`.
  Not implemented: session tickets, early data.
- [RFC 9002, QUIC Loss Detection and Congestion Control](https://www.rfc-editor.org/info/rfc9002) (Proposed Standard, May 2021).
  Takes: RTT estimation (5.3), loss detection, and the Reno controller (7) that is the default.
  Not implemented: nothing removed.
- [RFC 6582, The NewReno Modification to TCP's Fast Recovery Algorithm](https://www.rfc-editor.org/info/rfc6582) (Proposed Standard, April 2012).
  Takes: one window reduction per loss episode.
- [RFC 9438, CUBIC for Fast and Long-Distance Networks](https://www.rfc-editor.org/info/rfc9438) (Proposed Standard, August 2023).
  Takes: the opt-in `"cubic"` controller.
  Not implemented: conformance to every section was not checked.
- Cardwell, Cheng, Gunn, Hassas Yeganeh and Jacobson, [BBR: Congestion-Based Congestion Control](https://doi.org/10.1145/3012426.3022184), ACM Queue 14(5), 2016.
  Takes: the opt-in `"bbr"` controller: bottleneck bandwidth and round-trip estimates, pacing.
  Not implemented: BBRv3 of [draft-ietf-ccwg-bbr](https://datatracker.ietf.org/doc/html/draft-ietf-ccwg-bbr-07); loss is not a signal.
- [RFC 8899, Packetization Layer Path MTU Discovery for Datagram Transports](https://www.rfc-editor.org/info/rfc8899) (Proposed Standard, September 2020).
  Takes: path MTU discovery above 1200 bytes.
- [RFC 9846, The Transport Layer Security (TLS) Protocol Version 1.3](https://www.rfc-editor.org/info/rfc9846), section 7.5 (Proposed Standard, July 2026; obsoletes RFC 8446).
  Takes: the exporter behind `Conn.ExportKey`.
